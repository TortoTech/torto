## Code and quotation groups
Read complete literal `body` text for `targets.classify_code_or_quote`, including every line and its surrounding explanation. These authored containers are eligible, not protected boundaries.
`container_runs` lists adjacent candidates to consider together. Adjacency, matching fonts and matching source types do not prove a single group.
Jointly decide membership AND presentation in one response. Return one `code_or_quote` per confident group: consecutive complete container IDs in `body`, `presentation`, optional `language`, and attached `captions`/`sources`. A one-member body preserves an independent example. Do not first classify individual members and then decide whether to merge them. Do not also return another quote proposal for any member of the same group.
- Combine fragments that continue the same excerpt or technical example. Keep separate examples separate when context changes topic, credit or purpose. Never cross intervening narrative, headings, images or tables; never group ordinary paragraphs because they end with a colon.
- `presentation: code` covers program/configuration/markup examples as a whole. Opening/closing tags, attributes, CSS rules and natural-language XML/JSON values can belong to one example. HTML containing a style element and HTML markup is one HTML example, not separate CSS and HTML groups. Malformed illustrative snippets may still be code.
- A WEBVTT header, timestamps and subtitle sentences form one technical example, not alternating code/quotation groups. Return a confident supported language or null; unsupported syntax remains plain preformatted text.
- `presentation: quote` covers quoted prose and authored non-program specimens, including dialogue/stage directions when the publication already placed them in quotation containers. Keep original paragraph boundaries. Small inline code fragments do not make the whole quotation code.
- Authored preformatted structure is supporting evidence, not proof. Monospace fonts or class names alone are insufficient: recipes, chat, email, emoticons and punctuation specimens can be prose.
- Example: a WHO definition followed by a separate quotation container containing its WHO signature is one quote body plus a `sources` attachment. Two RNIB statement paragraphs followed by a named signature are one two-member quote body plus a source. Do not bury a signature in body or treat it as an independent quotation.
- `captions` and `sources` contain only adjacent explicit labels/captions or written credits, outside body, in authored order. A source may itself be an authored quote container. Do not attach unrelated narrative or invent a credit. Empty arrays mean absent attachments.
- For prose only, `body_index` can identify the final eligible explicit-credit paragraph INSIDE the LAST body member. Otherwise null. Never treat a code line as attribution. Preserve existing explicit attributions; do not join across different credits.
- For a single quote with an exact terminal inline credit and no multi-container grouping, the existing `quote_inline` schema may be used.
Keep every original character, line break, indentation and URL/link spelling. Never replace code/quote URLs with website icons or rewrite examples.
Do not select inline citations or formulas inside any member of a group classified as code. Omit uncertain groups rather than forcing a merge or a language.
