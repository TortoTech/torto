# Local PDF reflow

The PDF toolbar has one text-generation button. A worker samples up to 12 deterministically distributed pages and chooses local reconstruction or the configured OCR provider. Existing results for the chosen source are reused. The UI does not display classification labels or reasons. Right-click to regenerate automatically or explicitly select/regenerate a local result or select existing OCR text. Sampling and local conversion can be cancelled with the same button; a running shared OCR job retains its existing background lifecycle.

The preflight combines visible/hidden text, the union of clipped image rectangles (including tiled scans), Unicode mapping failures, replacement/private-use characters, abnormal whitespace, repeated text at the same coordinates, and native layout limitations. Blank and sparse illustration pages are excluded from the body vote. At least 75% of informative sampled pages must have reliable native text; otherwise the button uses OCR. Sampling inspects objects without decoding images or rendering pages, and releases each page before inspecting the next. Conversion retains page-level fallbacks and repeats text-quality checks on unsampled pages. Classification is a conservative heuristic, not proof of PDF provenance or correct reading order. No OCR request is made when recognition is disabled; the existing settings instruction is shown instead.

Reference implementations: [MinerU 2.5.4 sampling classifier](https://github.com/opendatalab/MinerU/blob/mineru-2.5.4-released/mineru/utils/pdf_classify.py), [Marker text-quality checks](https://github.com/datalab-to/marker/blob/master/marker/providers/pdf.py), and [OCRmyPDF visible/hidden text analysis](https://github.com/ocrmypdf/OCRmyPDF/blob/main/src/ocrmypdf/pdfinfo/info.py). Their thresholds are not treated as universal guarantees.

The implementation borrows the staged layout approach from [LiteParse](https://github.com/run-llama/liteparse/tree/main/crates/liteparse/src/markdown_layout), using Torto's existing Hayro interpreter and direct publication IR. It adds no PDFium process, Python environment, model download, or Markdown round trip.

## Processing

1. Read the document catalog's optional `/Lang` string into publication metadata, preserving regional and non-English tags and leaving missing/empty values unspecified. Conversion refreshes a legacy descriptor's missing language from the opened PDF and persists it in both original and reflow descriptors; explicit caller languages remain unchanged. This gives the existing paragraph hyphenator its language fallback without guessing English or opening the PDF during native reading.
   Interpret one page at a time. Extract Unicode, baseline/advance coordinates, font metadata, marked-content tags and MCIDs, image bounds, graphics, ruling, and URI annotations. Use the same page transform as rendering. Unmapped glyphs keep geometric placeholders so their lines can fall back to images.
2. Save intermediate pages on disk. Accumulate a body-size histogram and edge-line occurrences. Header/footer candidates must be short, at the outer 18% of the page, at body size or smaller, separated from the next body row, and not tagged as headings. Compare normalized text, vertical position and font size within ten neighbouring pages on either side, including alternating page headers. Require three occurrences, or two when an outer token is a page number. Normalize whole digit runs so page 99 and page 100 still match. Repetition alone cannot remove text from the body.
   A single-occurrence running title can inherit a confirmed layout only with three nearby confirmed support pages of the same parity, matching edge/vertical position, outer-counter alignment, font size and printed-page offset. Its title must also match the outline context for that physical page; title-free page numbers use the same geometric/counter evidence. Missing counters, unknown titles and uncertain layout matches stay visible. Outline intervals end at the next sibling heading, so an earlier section does not authorize unrelated later headers.
   Group ordinary glyphs around fixed baselines before horizontal sorting. Use character-weighted median font/baseline metrics, so a large section ordinal cannot pull in the next row or turn prose into a heading. After splitting horizontal gaps, attach smaller raised/lowered runs using baseline proximity, vertical overlap and horizontal collision checks. Allow rounding error at the 80% script/body font-size boundary; separate small-print rows stay independent. Paragraph continuation measures ordinary prose bounds rather than large margin ordinals and preserves first-line indentation boundaries.
3. Identify ruled and conservative borderless tables before column ordering. Cells exclusively own their glyphs. Incomplete grids and uncertain formula lines retain raster regions. Extract figures and captions, headings, prose, list markers, and confidently matched superscript/bottom notes.
   Outline labels can confirm titles split across up to four nearby aligned lines and standalone division ordinals. A large margin ordinal at the following body-row baseline can be reassigned only when it matches the outline and the nearby title. Emit `HeadingOrdinal` plus `Heading` blocks for the existing unified/bilingual heading composer, with one size scale and physical per-glyph provenance; preserve ordinary numeric prose prefixes. Ambiguous repeated titles and incomplete groups remain unchanged.
   Before emitting prose, group nearby subimages with at least two distinct panel labels referenced by a shared figure caption. Labels must lie just below the corresponding images; intervening text and unrelated regions reject the group. Save the images and labels together in one crop, preserving panel layout and exclusive glyph ownership. A single picture containing several panels uses the same rule. The caption remains selectable and translatable text outside the crop. Grouping also considers references on wrapped caption lines.
   Figure captions directly following an image compare continuation indentation against the title text after the numbered label, rather than a label set in the left margin. Matching caption font, line spacing and title alignment keep wrapped lines together; a new caption, heading, list or body-font change ends the caption. For ASCII line-end hyphens inside a confirmed caption, remove the hyphen only when the complete joined spelling appears independently in that same caption. Preserve source glyph ownership with a zero-width source slice for the removed hyphen. Other authored compounds retain their hyphens. This borrows the caption-led whole-figure grouping and separate caption-building approach of [PDFFigures2](https://github.com/allenai/pdffigures2), using the existing local geometry without adding a model runtime.
4. Order regular column bands around spanning objects. Join lines using geometry and typography. Cross-page joins compare indentation within each page's reliable single-column body frame, allowing mirrored inner/outer margins while retaining bottom-to-top, full-tail-line and terminal-punctuation checks. Sparse or multi-column pages keep the conservative absolute-position fallback. Notes do not interrupt body continuation. A confirmed PDF image with a complete caption can float inside an unfinished paragraph: matching body font, column/indent, physical ordering and continuation geometry allow the text before and after it to become one paragraph, followed by the image and its caption. Same-page joins require a full tail row; cross-page joins require reliable single-column frames and a bottom-to-top gap explained by the figure when present. Previously moved figures do not block later continuation of that same paragraph. Terminal punctuation (including closing quotes), a new paragraph indent, lists, headings, tables, formulas and uncertain raster regions remain boundaries. English compounds keep their hyphens; discretionary soft hyphens are removed. Chinese joins do not introduce spaces.
5. Write sections on an eight-page storage cadence, respecting top-level authored/generated chapters. Resolve a leading continuation before saving a storage cut; only the joined paragraph and leading figure move to the preceding chunk. If that consumes the complete next page, allow one page of boundary spill rather than writing an empty spine item, with a hard nine-page limit. Preserve inline link destinations while retargeting moved source ownership, Unicode character offsets and physical/outline anchors. Resolve page and outline URLs from their final anchor owners. Physical-page anchors and outline coordinates map to section/source positions. Per-glyph provenance retains physical page, bounds and reconstructed character offsets.

Clipped/raster resources are saved during conversion. Reading the result never requires the original PDF. The original file is opened by the conversion job or by an explicit original-view/tool request; its interpreter/font data is released with the job.

## Storage and lifecycle

`pdf-native/<book-id>/<generation>/` contains a manifest, `sections/*.json`, and `resources/*.png`. A successfully completed generation is published through an atomic `current.json`. Cancellation and failed imports cannot expose partial sections or replace the previous pointer. A loaded reader leases its exact immutable generation even if cloud sync publishes a newer one.

The source retains its descriptor and one prepared section; per-glyph provenance stays on disk. Section and image loading uses the existing bounded reader caches. Original/reflow switching uses the existing source retirement and raster ownership cleanup. Native and OCR have different spine/node identities; semantic recognition has a separate native cache identity. Translations belong to the source-specific reader instance and input identities. Existing OCR content and annotations are not overwritten.

Eight-page storage cuts carry the `rebook-continuation-section` spine property. The reader joins content before their first TOC target to the preceding subsection's focus view, even across several storage chunks. The compilation worker prepares only layouts intersecting that logical unit. Shared layout storage preserves source identities without duplicating page or image allocations; cache accounting includes every retained layout, and obsolete joined views remain evictable. The continuous view crops each part to its source content, removing blank page tails/heads at storage cuts. The unit's identity stays stable while scrolling between chunks, and subsection navigation skips synthetic continuation boundaries. True top-level chapter starts and real TOC targets at a chunk's first block end the join and retain their authored preludes. Physical cache chunks and classic paginated layouts remain separate; this does not repaginate classic pages across files or widen memory budgets. The source derives the hint from the original TOC and native page map when opening existing generations, so this boundary fix requires no PDF regeneration.

The conversion revision also versions native spine identities and semantic caches. Older generations stay on disk but are not loaded as current text; regenerate them from the PDF toolbar to apply updated layout rules.

Header detection follows the neighbouring-page association approach documented by [Refinedoc](https://github.com/CyberCRI/refinedoc#customize-windows-size), rather than requiring a chapter header to repeat across a fixed fraction of the entire book. [PyMuPDF4LLM](https://github.com/pymupdf/pymupdf4llm/blob/main/CHUNKING.md) also offers repeat detection; [Docling](https://github.com/docling-project/docling/discussions/1464) classifies page headers/footers with its layout model and excludes them from body export. Torto keeps its existing local interpreter and performs geometric/repetition checks in the conversion worker without adding a model runtime.

Cloud sync uses `derived/<book-id>/native-pdf.json` and `native-pdf.zip`, independently of OCR. Archives are cached by generation, checksummed, size limited, path checked, and rejected if local dirty revisions changed during transfer. Generation and source-selection preferences are local; choosing native text does not change another device's explicit OCR choice.

Sync planning retains archive paths and lengths. Each upload loads its own payload when executed, rather than holding every book's archive in memory for the whole batch.

## Conservative limits

The first version targets horizontal Chinese/English text and regular single/two-column layouts. Unreadable Unicode, substantial rotation, RTL text, full-page images (including scans with hidden OCR layers), complex formulas, and irregular ruled tables retain original images. Books without usable native pages stay on the existing PDF/OCR path.

Borderless reconstruction requires repeated aligned short rows with a distinct bold header; arbitrary free-form tables are not inferred. Complex merged cells are preserved as images. Marked-content tags, structure-tree MCID associations and outline matches help headings. Form scopes and conflicting associations fall back to geometry; a general structure-tree reading-order resolver and ActualText substitution are not implemented. Type1 fonts without accessible style metadata can retain plain styling. Ambiguous footnotes remain visible prose. These choices avoid inventing semantic content while keeping the complete visual region available.

## Shared OCR and native reflow normalization

Native revision 9 collects marginal candidates before font-size classification and validates their font against the document body distribution. Tiny diagram labels on one page therefore cannot turn its normal running head into a heading. Explicit tags, validated outline headings, body spacing, neighbouring-page repetition and singleton counter/context proof remain protections against removing content.

`rebook_formats::reflow` owns directory-validated heading promotion, semantic continuation barriers, styled text/source-offset joins and independent-spelling proof for line-end hyphens. Native geometry remains in the native adapter; glyph order, exact rectangles and per-glyph provenance are not inferred from OCR. OCR revision 2 uses the shared rules when a section is parsed on a reader worker. It keeps raw page Markdown intact, associates adjacent image/caption blocks, continues unfinished prose around captioned floats and preserves physical-page/TOC anchors after joins. Existing reader caches bound normalized IR; the source retains no additional full-book IR or DOM. Versioned OCR spine identities prevent reuse of incompatible semantic/translation entries. Existing OCR documents need no service call or destructive migration.

Without geometry, a floating-image continuation requires lowercase Latin evidence and an unfinished preceding paragraph. Chinese float joins need explicit provider continuation data. Complete sentences, headings, tables, lists, formulas and special-page images remain barriers. A hard hyphen stays unless an independent complete spelling in the section confirms the split; soft hyphens can be removed without that proof. OCR recovery cannot reconstruct recognition content that was never returned.

New OCR results retain compact optional block roles, coordinate boxes and explicit continuation flags. Content digests avoid duplicating prose; uncertain/duplicate matches are not applied. Explicit provider header/footer/page-number roles remove matching marginal blocks while advancing their anchors to real content. MinerU image captions are selectable captions rather than image alt text. The supported provider fields follow the [PaddleOCR-VL result contract](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/pipeline_usage/PaddleOCR-VL.en.md) and [MinerU output contract](https://opendatalab.github.io/MinerU/reference/output_files/). Missing fields remain optional; stored boxes do not fabricate glyph geometry or page dimensions.

## Generation performance diagnosis

An instrumented V10 conversion of the 812-page *Pick, Click, Flick!* book took approximately 148.8 seconds on an Intel Core i7-6800K (6 cores / 12 threads). A desktop build overlapped this diagnostic run, so these values locate bottlenecks rather than establish an idle benchmark or a speedup. The headless tool took 169.4 seconds including post-generation parsing/provenance checks; those checks are not part of the desktop conversion job.

| Stage | Seconds |
| --- | ---: |
| PDF page rasterization | 94.6 |
| Native text extraction | 15.6 |
| Image copying, cropping and PNG writes | 12.4 |
| Intermediate JSON writes / reads | 2.9 / 7.7 |
| Layout, paragraph recovery and bookkeeping | 9.5 |
| Heading / marginal-text analysis | 2.7 |
| Section writes | 2.3 |

In the V10 diagnostic, only 370 pages needed rasterization, but each rendered the complete page before creating its crops (550 resources including 40 full-page fallbacks). Rasterization accounts for approximately 64% of conversion time. That renderer constructed a fresh Hayro RenderCache for every page; font outlines and interpreter resources could not be reused between pages. The encoder's default PNG compression is already Fast.

The diagnosis identified three priorities: a bounded, worker-local render cache, direct export of simple embedded images with proven transforms/clipping/transparency, and a renderer crop-rectangle interface for complex/vector figures. Hayro 0.7.1 exposes output viewport dimensions but no crop-origin offset, so width/height alone cannot implement an arbitrary region render. Any cache reuse or parallel rasterization needs explicit memory bounds; image fidelity and the current atomic-generation/source-provenance contract must remain intact. The diagnostic pass changed only instrumentation; implementation is described below.

ConversionTimings accumulates lightweight stage totals only on the conversion worker, and is excluded from serialized manifests. The `pdf.native.converted` lifecycle log records one summary per completed conversion, including release builds. The 659 manifest, section and image outputs were byte-identical to the previous V10 conversion.

The toolbar uses the shared LoadingSpinner while generating, preserving its 32px footprint, progress tooltip and click-to-cancel behavior. Hidden toolbar actions do not instantiate the spinner; the existing shared widget paces repaint at 30 FPS when focused and 10 FPS when unfocused, and stops when hidden.


## Generation performance implementation (native V11)

Conversion reuses an 8 MiB accounted outline cache on its own worker. Decoded font/image/color objects are released before each physical page; no PDF render cache is added to the reader. Cache tests compare actual rendered pixels with fresh caches under zero and small budgets and across page resets. A single page can still require transient decoded image/compositing memory; the outline limit is not a bound on total process working set.

Proven isolated, opaque embedded images can bypass page rasterization. Eligibility requires an upright axis-aligned transform, a complete rectangular clip, no masks or non-normal compositing, and no intersecting text, graphics or other pictures. The PDF interpreter's existing image decoder handles CMYK, calibrated/indexed colors and decode arrays. The renderer's original image sampling pipeline preserves crop pixel dimensions, white margins and the image's display size. Failed/unsupported decodes use the ordinary region path.

Complex figures use one padded union viewport per physical page. The local viewport starts on Vello CPU 0.0.8's 256 x 4 wide-tile grid. Merely subtracting an arbitrary integer origin changed edge coverage for some images; the grid alignment removes the observed narrow edge-column discrepancies. The added `hayro::render_region` retains page rotation, nonzero page origins, masks, clipping and compositing. Decoder resolution hints use transformed vectors rather than translated points so viewport location cannot change the decoded resolution. Cropping copies only saved crop pixels rather than a second full-page RGBA bitmap.

The small vendored Hayro 0.7.1 patch retains upstream MIT/Apache licenses and is documented in `third_party/hayro/TORTO_PATCHES.md`; the interpreter and syntax dependencies stay upstream. Native V11 isolates existing semantic/translation caches and requires regenerating old native results. OCR normalization and original-PDF lifetime policies are unchanged.

Validation includes rotated/clipped/alpha-masked synthetic pages, rejection of unsafe direct-export candidates, complete-book unique glyph/anchor/link audits, seven floating-paragraph fixtures and real image crops from 14 physical pages. The earlier unaligned viewport test exposed an edge discrepancy; after tile alignment, all 27 sampled real-book crops matched full-page rendering pixel-for-pixel.


A quiet local comparison on the same i7-6800K machine and the same dev optimization profile measured V10 conversion at **130.0 s** and the final V11 conversion at **109.9 s** (about **15.4% less elapsed time**). Full/region rasterization fell from 79.8 s to 65.2 s. The headless verification tool took 122.2 s including its extra post-generation parsing checks; those checks are not desktop generation time. The final run used 328 regional page viewports, retained 40 full-page fallbacks and directly exported 2 isolated images. Most figures in this book have clipping, overlays or grouped content and therefore use the conservative region path.

All 550 output image dimensions matched V10. Of those resources, 362 were byte-identical and the remaining 188 differed by at most 2 levels per 8-bit RGB channel; no narrow high-contrast edge discrepancies remained after tile alignment. All 812 physical pages, 108 sections, 1,748,551 retained source glyphs, 1,456 anchors and 31 internal links passed the complete-book source audit. The job's measured peak working set was approximately 379 MiB; this is a headless generation process measurement, not desktop resident memory, and no equivalent pre-change peak was recorded.

## Bounded native image pipeline

Native generation now submits image pages to up to four scoped workers while the conversion worker continues ordered semantic layout, float recovery, section writes and source mapping. All workers use the same raster path, resolution, crop grid, color decoding and PNG settings. Scheduling alone retained V11; the subsequent renderer upgrade below advances generation to V12 because some derived pixels change.

The queue is bounded by worker count. A shared 192 MiB scheduling budget accounts for queued and active page geometry, estimated decoded image buffers, raster/compositing buffers, the largest saved crop and an 8 MiB outline allowance per job. A page whose estimate exceeds the budget is admitted alone. This is a conservative scheduling estimate, not an allocator limit or a bound on process working set: complex PDF decoders and compositing layers may require additional transient memory. Each worker creates its own renderer cache and releases decoded fonts/images/colors after each page; only bounded outlines remain until the conversion ends. The original PDF is shared, and no renderer/interpreter cache is shared across workers or retained by the reader.

Cancellation or image-write failure stops admission and discards queued work. Every worker is joined before returning, so staging cleanup cannot race image writes. The final image barrier must succeed before writing the manifest or publishing the generation. Worker panics are converted to generation errors. Queue/budget waits occur only on the background conversion worker; image workers sleep on the queue rather than polling the UI.

`raster_ms` and `image_write_ms` now sum worker durations and may overlap each other and layout. `raster_wait_ms` measures producer backpressure plus the final image barrier on the conversion worker; only this wall time is subtracted from layout elapsed time. `raster_workers` and `raster_peak_estimated_bytes` report worker count and peak budget reservation. None of these diagnostics enters the synchronized manifest.

Pipeline regressions check byte-identical serial/parallel PNGs for isolated images, rotated pages, clipping, masks and text overlays; failed writes and cancellation; oversized-page admission and permit release. Whole-book comparisons must use equivalent builds, with no concurrent compilation, and compare manifest/section/image bytes as well as conversion time. The existing dev-profile benchmark must not be compared directly to release-profile times.

On the same i7-6800K (6 cores / 12 threads), quiet release-profile conversions of the same 812-page book took **61.3 s** and **62.1 s** with the preserved serial executable. The final bounded pipeline took **29.2 s**, approximately **53% less elapsed time** than the instrumented 62.1 s serial run. Its diagnostic tool took 35.8 s including post-generation reading/provenance checks; those checks are excluded from conversion time. No compilation overlapped these runs, and no GPU was used. These results do not compare release performance to the earlier 109.9 s dev-profile measurement.

All **659 output files** (manifest, 108 sections and 550 PNG resources) were SHA-256 identical to the serial result. The pipeline retained 328 regional viewports, 40 full-page fallbacks, 2 direct image exports and 211,758,459 rasterized pixels. Process peak working set, sampled through the process peak counter every 50 ms, was **378.8 MiB serial** and **389.3 MiB parallel** (about 10.5 MiB higher). These are isolated headless conversion process measurements, not desktop resident memory. Peak scheduling reservation was approximately 191.9 MiB, within the 192 MiB admission budget. Runtime evidence is stored under `target/pdf-native-parallel-final-comparison.json` and the matching release benchmark logs.

## Vello CPU 0.3.0 upgrade experiment

On 2026-10-09, the vendored Hayro adapter was temporarily migrated from Vello CPU 0.0.8 to 0.3.0. The interpreter, native layout, four-worker pipeline, crop alignment, sampling quality, resolution and PNG settings were unchanged. The migration used the new `render` and `pop_clip` APIs and explicit premultiplied pixel metadata. It kept the u8 raster pipeline and disabled internal renderer threading. See the [upstream changelog](https://github.com/linebender/vello/blob/main/vello_cpu/CHANGELOG.md) for the rendering API and sampling changes.

The same release-profile diagnostic and 812-page PDF were used on the same i7-6800K, with no concurrent compilation or GPU generation. Runs alternated 0.3.0, 0.0.8, 0.3.0, 0.0.8. Conversion time excludes post-generation reading and provenance checks.

| Version | Conversion runs | Mean conversion time | Sum of worker raster time, mean | Process peak working set |
| --- | --- | --- | --- | --- |
| 0.0.8 | 28.38 s, 28.73 s | 28.55 s | 33.33 s | 388.1–405.7 MiB |
| 0.3.0 | 28.25 s, 28.39 s | 28.32 s | 32.69 s | 392.6–397.7 MiB |

The mean whole-book difference was only **0.8%**, smaller than the observed 0.0.8 run-to-run spread. Two runs per version do not establish a stable speed improvement. Summed worker raster time was approximately 1.9% lower, but this overlapping duration is not whole-book wall time. No meaningful memory reduction was established.

All 109 manifest/section files and 504 of 550 PNG resources were SHA-256 identical. All image dimensions matched, but 46 images had pixel changes, including differences greater than 16 color levels at some edges. The largest mean RGBA channel difference among changed images was 0.235 on the 0–255 scale. Visual checks of the two images with the largest mean differences found no missing content; these checks do not prove equivalent quality across every changed image. This is not evidence that the new renderer is worse, but the upgrade cannot claim unchanged pixels.

The initial performance experiment passed 104 format tests and a separate 27-image real-book check confirming pixel-identical region versus full-page sampling under 0.3.0. It did not establish a worthwhile generation speedup. The upgrade was subsequently **retained for rendering correctness**, after expanding evaluation to all reader uses of Vello CPU. The measurements above precede the generation revision and cover/backend dependency alignment described below; they do not establish a UI performance improvement. Evidence and the initial migration patch are under `target/vello030-comparison.json`, `target/vello030-experiment.patch` and the `target/pdf-native-vello*` benchmark logs and generated directories.

### Reader-wide adoption

All three production CPU-rendering uses now share Vello CPU 0.3.0:

- Vendored Hayro renders original PDF pages, future OCR input/special-page images and native image exports. Existing stored OCR resources are preserved.
- AnyRender's CPU backend renders generated first-page covers for books with no usable cover. It is upgraded to 0.18.0 with AnyRender 0.14.0, retaining the existing bounded image cache and disabled internal multithreading.
- Vendored epaint rasterizes interface glyph outlines. It is upgraded from 0.1.0 to 0.3.0 and flushes the context before rendering. Hinting, subpixel bins, font selection and atlas color transfer are unchanged.

The [filtered-image boundary fix](https://github.com/linebender/vello/pull/1950) corrects mismatched interpolation weights and texel indices, while the [opaque-image mask/blend fix](https://github.com/linebender/vello/pull/1697) and layer-clipping fixes improve renderer correctness in the PDF/cover drawing paths. These are applicable code-path improvements, not a claim that each defect was observed in the current library. A focused regression checks the two-color repeated-image boundary against its known correct color. Pixel differences from 0.0.8 therefore need correctness assessment rather than blanket rejection.

AnyRender 0.14 carries explicit clip fill rules. The desktop GPU adapter now forwards those rules instead of assuming nonzero winding, preserving recorded scenes' clipping semantics. This does not change the GPU renderer version. Ordinary book SVGs, body/chat formulas and chat SVG assets continue to use resvg/tiny-skia; their rendering is not attributed to this CPU upgrade.

Native generation advances to **V12** so old derived image/translation/semantic caches are not mixed with changed renderer output. Existing library data is not rewritten during validation. Regenerating a native result uses the usual staged conversion and publication path.

## Lossless binary page spool

Conversion-only `raw/` pages now use bincode 1.3.3, already present in the dependency graph, instead of JSON. Published sections, manifests and synchronized reading data keep their existing JSON format. The temporary codec preserves every glyph, coordinate bit, image reference, obstacle, structure tag, link and outline association. It uses explicit fixed-width integer encoding, little-endian floats, a 32 MiB per-entry limit and trailing-byte rejection. Reads retain at most one bounded byte buffer; pages are deleted after use. Writes explicitly flush the buffer and propagate errors. The spool lives only within one staged conversion, so it needs no old-data migration or separate generation revision.

Two quiet release-profile runs per implementation alternated binary, JSON, binary, JSON on the same 812-page PDF and i7-6800K. Both implementations include the same four-worker pipeline and Vello CPU 0.3.0; compilation and output hashing did not overlap timed runs. Times exclude the diagnostic tool's post-generation source checks.

| Temporary format | Conversion runs | Mean conversion | Mean spool write + read | Peak process working set |
| --- | --- | --- | --- | --- |
| JSON | 28.31 s, 28.57 s | 28.44 s | 5.32 s | 388.6–395.7 MiB |
| Binary | 25.59 s, 25.21 s | 25.40 s | 1.23 s | 390.0–393.4 MiB |

Whole-book generation was approximately **10.7% faster**, and temporary I/O/serialization time fell approximately **76.9%**. The full reduction in spool time does not translate into wall-time savings because the old second-pass reads overlapped raster workers. No meaningful process-memory improvement was established.

All **550 PNG resources** were SHA-256 identical. File sets, 108 sections, all strings and nonnumeric JSON content, chapter ownership and statistics matched. This is not whole-output byte equality: preserving original coordinate bits instead of JSON reader rounding changed 632,133 coordinate number tokens, with a maximum absolute difference of **7 × 10^-14**. Two coincident glyph IDs on page 4 exchanged order in provenance; they retain the same source node and coincident rectangles, with unchanged reading text. A structural JSON comparison and a separate numeric-token comparison isolate those differences; neither uses image-quality sampling to excuse changed pixels.

Validation passed **107 format tests**, including exact binary field/float round trips, malformed/truncated spool rejection, staged conversion/cancellation and serial/parallel image regressions. The real-book floating-paragraph cases and desktop native-navigation regression passed against the binary generation. Both binary runs produced **659 SHA-256-identical files**, confirming repeatable output under this fixture. Evidence is under `target/page-spool-*-comparison.json`, `target/page-spool-benchmark-summary.json` and `target/pdf-native-{binary,json}-spool-*.log`.

Of the four proposed optimization areas, image parallelism and layout/raster pipelining are implemented, and the binary spool is now implemented. Resource reuse remains partial: rendering workers retain bounded outlines and the PDF shares its parsed stream cache, but extraction and raster interpretation do not share decoded-font caches or replayable page scenes. The interpreter cache currently exposes no byte-budget or eviction interface; retaining it across both whole-book passes would conflict with bounded memory. Cross-pass command/resource reuse has not been implemented or benchmarked, and the measurements above must not be attributed to it.

## Persisted coordinate precision

Per-glyph provenance rectangles now serialize to at most four decimal places in final section JSON. Extraction, geometric grouping, glyph ordering, raster bounds, matrices, and binary page spooling retain their original precision. The serialization error is approximately at most 0.00005 page-coordinate units per component; zero is canonicalized to positive zero. Source ranges, character offsets and original glyph IDs remain exact. The V12 schema and source identities are unchanged, so existing generations remain readable. Regenerate local reflow to obtain compact provenance.

The workspace explicitly enables serde_json's `float_roundtrip` feature. The desktop already received it transitively from Rig, but formats-only builds previously used best-effort float parsing. This removes that build-dependent behavior; it does not mean desktop JSON parsing was previously imprecise.

The final 108-section, 812-page fixture reduced section JSON from 489,966,556 to 429,109,050 bytes (60.9 MB, 12.42%). After canonicalizing only provenance rectangle numbers, every section was byte-identical to the preceding binary-spool generation. All 550 PNG resources, book navigation and physical-page targets matched. This is a storage measurement, not a measured conversion-speed or live-memory improvement: an in-memory f64 still occupies eight bytes. The unchanged binary spool remains lossless. Evidence is in `target/float-precision-final-comparison.json`; the final generated fixture is `target/pdf-native-precision-final`.

## Separate, lossless source mapping

New generations keep reading IR in `sections/{index}.json` and store per-glyph source mappings in `resources/provenance-{index}.bin.z`. A node dictionary removes repeated spine/node strings; varint integer encoding preserves Unicode offsets, physical page numbers and original glyph IDs. Coordinates retain their complete f64 bits, including signed zero, rather than the previous JSON's four-decimal presentation. The sidecar has its own `TRTPRV01` format header and zlib integrity check. Compressed and decompressed payloads are independently limited to 32 MiB, and truncated, trailing or invalid dictionary references are rejected.

Normal reading loads only IR. It also skips deserialization of provenance in existing combined JSON files. Explicit source-mapping queries decode one sidecar on demand; no whole-book mapping cache is introduced. Import validates mappings on its background worker before publishing the staged generation. Every sidecar is listed in manifest resources, so existing archive export paths include it and older clients preserve it during synchronization. New section JSON retains an empty legacy `provenance` field: older clients can display the reading IR but need the new implementation to query the sidecar's mapping. New clients continue to read old combined JSON in full. The optional storage extension leaves V12 source identities, navigation and semantic/translation cache keys unchanged. Existing immutable generations are not rewritten automatically.

Packing and compression buffer only one bounded section at a time. Feeding bincode directly into zlib was rejected after the first measurement: compressing thousands of individual tiny writes took 20.60 s across section writes. A single bounded binary buffer reduced section writes to 1.17 s in the final whole-book run. That buffer preserves every coordinate bit and is released after the section write.

## Lossless image storage

Both regional raster crops and isolated-image exports now use one PNG encoder. It selects gray or RGB channels only when **every** RGBA pixel proves the conversion exact; any transparency keeps RGBA. Channels are compacted in the existing crop buffer. Default compression and adaptive filtering replace Fast RGBA encoding. Renderers, resolution, sampling, crop geometry, color conversion and alpha blending are unchanged.

JPEG is appropriate for photographs, but newly encoding rendered crops is lossy and can damage screenshots, formulas, subfigure labels and thin lines. The current direct-image path also samples PDF images and composes their crop margins; retaining the original JPEG byte stream is not a general replacement for that operation. No automatic lossy conversion or heuristic photo classifier is enabled by this change. The image optimization preserves decoded pixels exactly. Storage savings do not imply smaller decoded textures or GPU allocations.
